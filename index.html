Pages ↔ Local Docker Bridge

Five of your repos use the same architecture: a static GitHub Pages frontend that probes a localhost Docker backend and degrades gracefully when the backend is absent. This page is the audit of that pattern — the detection contract, the verbatim fallback strings each repo emits, and the generic docker compose up -d upgrade path. It contains no OCR, CAD, or RAG code; only the bridge.

The one-sentence contract: the page loads with zero backend, prints a verbatim reason why advanced features are unavailable, and unlocks them on the next reload once docker compose up -d is running locally.

1 Recognise the static-first contract

The Pages site is not a proxy to a server. It is a complete UI shell that runs entirely in the browser. Every advanced feature is behind a capability check, not a hard dependency.

Two consequences:

  • The site is fully usable (with reduced features) with no Docker.
  • Running Docker is an upgrade, never a prerequisite.

The audit confirmed this in all five repos: each ships a static frontend and a Dockerfile.backend (or server/) that is optional at load time.

2 The probe: how the frontend detects the backend

On load, the frontend issues a short-timeout fetch() to a known localhost port. The port varies by repo — 8080 in ram-catalog-app[reference:10], another port elsewhere — so the probe must be configured per repo, not hard-coded globally.

// Generic probe — adapted per repo's backend port.
async function probeBackend(port = 8080, timeoutMs = 1200) {
  const ctrl = new AbortController();
  const timer = setTimeout(() => ctrl.abort(), timeoutMs);
  try {
    const res = await fetch(`http://localhost:${port}/health`, {
      signal: ctrl.signal,
      cache: "no-store",
    });
    return res.ok;
  } catch (_) {
    return false;
  } finally {
    clearTimeout(timer);
  }
}

Timeout matters. A 1.2 s cap prevents the page from hanging when nothing is listening. cache: "no-store" ensures the probe reflects the current Docker state, not a cached “offline” response.

3 The fallback: print the verbatim reason

When the probe fails, the UI must not silently hide features. It must print the exact string the repo ships, so the user knows what is missing and how to fix it. The audit captured three distinct fallback styles:

// hardened-agent-harness-explainer
"static mode — limited (no localhost backend — run: docker compose up -d)"

// receipts-ocr-rag
"Backend Offline"   // plus: Entries: 0 · Code Blocks: 0 · Errors: 0

// receipts-ocr
"Checking Docker connection..."
"Docker backend unavailable, using Tesseract.js fallback"

These are not generic error toasts. They are contract statements that tell the user exactly which command to run (docker compose up -d) or which fallback engine is active (Tesseract.js).

4 The upgrade: docker compose up -d

The advanced features live in the local Docker instance. The generic upgrade path is the same across the audited repos:

git clone https://github.com/swipswaps/<repo>.git
cd <repo>
docker compose up -d

# Then reload the Pages site — the probe should now succeed.

Ports must match the probe. If docker compose binds the backend to 8080, the frontend must probe 8080. ram-catalog-app already moved its host port to 8080 specifically to avoid TIME_WAIT collisions[reference:11].

Firewall: some repos include start.sh / stop.sh to manage firewall rules and PID tracking. If the probe fails while Docker is running, check that the host port is reachable from the browser (curl http://localhost:8080/health).

5 Verify detection without the browser

Use the helper script to reproduce the browser probe from the shell. It takes the backend port as an argument and prints the verdict in the same terms the page uses.

bash scripts/bridge-check.sh 8080
# advanced-mode: available
# or:
# advanced-mode: limited (connection refused on localhost:8080)

The script also prints the verbatim fallback string the page would show, so you can confirm the contract end-to-end.

6 What “advanced features” means (audit-derived)

The audit did not need to read the OCR/CAD/RAG code to establish the contract. The observable advanced features are:

  • Higher-accuracy engines — PaddleOCR instead of Tesseract.js (receipts-ocr).
  • Server-side export formats — GLB, OpenFOAM, XLSX (ram-catalog-app, solar-nostoc-cad-bridge).
  • RAG retrieval — code blocks, error patterns, success rates (receipts-ocr-rag).
  • Streaming logs and health checks — real backend logs rather than fake spinners (receipts-ocr).

Each of these is unlocked by the same probe-and-upgrade contract. The code behind them is repo-specific and out of scope for this page.

Done. You now have the audit, the detection contract, the verbatim fallback strings, and a shell-level verifier. The pattern is identical across all five repos.

Safety notes

  1. No code leakage. This page documents the bridge contract only; it contains no OCR, CAD, or RAG implementation.
  2. Ports are explicit. Never assume 8080 globally — each repo chooses its own port and the probe must match.
  3. Probe timeout is bounded. A hung fetch without AbortController would freeze the page; every probe must cap itself.
  4. Fallback strings are contract. Do not replace them with generic toasts — they tell the user exactly what to run.

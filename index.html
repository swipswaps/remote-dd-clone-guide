Remote dd Clone: SATA → USB‑Attached SATA over SSH

This page walks you through cloning a running SATA disk to a USB‑attached SATA disk from a remote machine over SSH, with live progress. The USB disk is attached to the machine you are sitting at; the source SATA disk is on a remote host you can reach with SSH. No prior dd experience is assumed.

Stop. dd writes raw bytes. If you point of= at the wrong device you will destroy that disk. Every command below includes a verification step before any write. Do not skip it.

What you will need

ItemWhy
SSH access to the source hostThe source SATA disk lives there.
sudo on both endsdd needs raw device access.
The USB‑attached SATA diskThe target. It must be at least as large as the source.
Optional: pvGives a real progress bar with ETA. apt install pv or dnf install pv.
Optional: pigz / lz4Compresses the stream to reduce SSH bandwidth.

1 Identify the source disk on the remote host

Log in to the source host and list its block devices. You are looking for the SATA disk you want to clone—not a partition, not the USB disk.

ssh user@source-host
lsblk -o NAME,SIZE,TYPE,MODEL,TRAN
sudo fdisk -l

Confirm the device name (for example /dev/sda). Check that TRAN is sata and the size matches the disk you intend to clone. Write the device name down.

2 Identify the USB‑attached SATA disk locally

On the machine where the USB disk is plugged in, list block devices again. The USB disk usually shows TRAN = usb or a model string containing “USB”.

lsblk -o NAME,SIZE,TYPE,MODEL,TRAN
sudo fdisk -l

Confirm the target device name (for example /dev/sdb). Triple‑check it.

Size check: the target must be at least as large as the source. Compare the SIZE column. If it is smaller, stop—a straight dd cannot clone to a smaller disk.

3 Unmount anything on the target disk

Before writing, make sure no partition on the target is mounted. Replace /dev/sdb* with your actual target device.

lsblk /dev/sdb
for p in /dev/sdb*; do
  [ -e "$p" ] || continue
  if findmnt -n "$p" >/dev/null; then
    sudo umount "$p" || echo "umount failed for $p — check: lsof $p"
  fi
done
if mount | grep -q ' /dev/sdb'; then
  echo "STILL MOUNTED: something under /dev/sdb is still mounted"
else
  echo "nothing mounted from sdb"
fi

If a partition is busy, umount prints target is busy and the loop echoes the exact lsof command to find the holder. Stop that process before continuing.

4 Dry run: confirm SSH and sudo work

Test that you can reach the source and run sudo without a password prompt blocking the pipeline. This is the most common failure point.

ssh user@source-host "sudo -n true && echo SUDO_OK"
ssh user@source-host "sudo blockdev --getsize64 /dev/sda"

The second command prints the source size in bytes. Keep it; you will use it for the progress bar later. If sudo -n fails, configure passwordless sudo for dd or use a root SSH key.

5 The clone: SSH + dd with progress

Choose one of the three variants below. All read from the source over SSH and write to the local USB disk.

A. dd's built‑in progress (no extra tools)

Available in GNU dd (coreutils ≥ 8.24). Lowest‑friction option.

ssh user@source-host "sudo dd if=/dev/sda bs=4M status=progress" \
  | sudo dd of=/dev/sdb bs=4M status=progress conv=fsync

B. pv progress bar (ETA, throughput)

Pass the source size with -s so the percentage is meaningful.

SRC_BYTES=$(ssh user@source-host "sudo blockdev --getsize64 /dev/sda")
ssh user@source-host "sudo dd if=/dev/sda bs=4M" \
  | pv -s "$SRC_BYTES" -b -t -r -e \
  | sudo dd of=/dev/sdb bs=4M conv=fsync

C. Compressed stream (slow CPU, fast network)

Use if SSH bandwidth is the bottleneck. pigz is parallel gzip; lz4 is faster but compresses less.

SRC_BYTES=$(ssh user@source-host "sudo blockdev --getsize64 /dev/sda")
ssh user@source-host "sudo dd if=/dev/sda bs=4M | pigz -1" \
  | pv -s "$SRC_BYTES" -b -t -r -e \
  | pigz -d \
  | sudo dd of=/dev/sdb bs=4M conv=fsync

With compression, pv's -s is the uncompressed source size, so the percentage still tracks correctly.

Why conv=fsync? It makes dd issue an fsync() before exiting, so data is on stable storage when the command returns. Without it, the shell prompt may appear before the writes reach the USB disk.

6 Monitor progress from another terminal

If you used variant A (only dd's built‑in progress) and want an extra update without stopping the copy, send SIGUSR1 to the dd process.

# Find the PID of the local dd writing to the USB disk
pgrep -a dd
# Then, in another terminal:
sudo kill -USR1

The running dd prints a record count and byte count to its stderr. Repeat as often as you like; it does not interrupt the copy.

You can also watch the target device's write activity:

iostat -dx 2 /dev/sdb
# or:
watch -n 2 'cat /proc/diskstats | grep sdb'
7 Verify the clone

After dd finishes, confirm that the first and last bytes match. This is a cheap sanity check—not a full hash of every byte, but it catches truncated or misdirected writes.

# Compare the first 1 MiB
ssh user@source-host "sudo dd if=/dev/sda bs=1M count=1" | sha256sum
sudo dd if=/dev/sdb bs=1M count=1 | sha256sum

# Compare the last 1 MiB (count from the end)
SRC_BYTES=$(ssh user@source-host "sudo blockdev --getsize64 /dev/sda")
SKIP=$(( (SRC_BYTES / 1048576) - 1 ))
ssh user@source-host "sudo dd if=/dev/sda bs=1M skip=$SKIP count=1" | sha256sum
sudo dd if=/dev/sdb bs=1M skip=$SKIP count=1 | sha256sum

For a full verification, run a hash of the entire device on both sides. This reads every byte and takes time, but it is the only way to be certain.

# Full hash (slow, but definitive)
ssh user@source-host "sudo sha256sum /dev/sda"
sudo sha256sum /dev/sdb
8 Finish: sync, power off safely, and boot

Flush any remaining writes and power off the USB disk cleanly before unplugging it.

sync
sudo udisksctl power-off -b /dev/sdb
# or:
sudo eject /dev/sdb

If the source disk was bootable, the clone should be bootable too. Boot the target machine with the USB‑attached SATA disk and confirm that it comes up. If it does not, revisit the bootloader stage—dd copied the raw disk, so the bootloader is on the clone, but firmware boot order may need adjusting.

Done. You cloned a running SATA disk to a USB‑attached SATA disk over SSH, with progress. The helper script in scripts/clone-remote-dd.sh wraps the most common path.

Command reference

CommandWhat it does
ssh user@host "sudo dd if=/dev/sda bs=4M status=progress"Reads the source disk and prints progress to stderr every second.
sudo dd of=/dev/sdb bs=4M status=progress conv=fsyncWrites stdin to the target, prints progress, and fsyncs before exit.
pv -s SIZE -b -t -r -eProgress bar with bytes, elapsed time, rate, and ETA.
sudo kill -USR1 PIDAsks a running dd to print its current statistics without stopping.
pigz -1 / pigz -dParallel gzip compress / decompress. Use lz4 for speed over ratio.

conv=fsyncFlushes data to stable storage before dd returns.

Safety checklist

  1. Target device confirmed? lsblk -o NAME,SIZE,MODEL,TRAN shows the USB disk's model and transport. Match it to the physical device you intend to overwrite.
  2. Target unmounted? Step 3 prints nothing mounted from sdb. If it prints STILL MOUNTED, stop and find the holder with lsof.
  3. Target large enough? The SIZE column for the target is ≥ the source.
  4. Source not changing? Cloning a mounted, actively written filesystem can produce an inconsistent image. For a running system, quiesce writes or accept that the clone is crash‑consistent.
  5. SSH and sudo tested? ssh user@host "sudo -n true" succeeds before you start the clone.
